### H5. The FOUR replacement architecture candidates

These are four distinct control strategies, selected as a useful benchmark shortlist from H4. They share a minimal safety/identity/proof broker because independent alternatives cannot fairly be compared by removing security from one. They differ in how goals become executable actions and when inference occurs. “Best” here means strongest relevant candidates to evaluate, not a demonstrated market ranking.

#### Alternative A — capability-compiled bounded programs and task graphs

**Mechanism.** Discover authorized capabilities with typed inputs/outputs, app/version/resource identity, preconditions, effect class, cancellation and verification. Compile direct user intent once into a bounded program or typed DAG. A local executor runs branches/loops/data transforms and safe parallel reads through capability RPCs. It returns compact typed results/proofs rather than sending every intermediate result back to the planner. Invoke the planner again only for genuinely new ambiguity or an exception; finish only after the independent manifest verifier passes. References R03/R05/R14/R17 support pieces; the proposed composition is our design inference.

**Why it could outperform the current mechanism.** A document/report transformation can run as one brokered native session instead of dozens of infer→queue→observe cycles. Reuse registered app object models and direct files; run one local batch with cancellation checkpoints and a durable effect journal. Local filesystem metadata or a cached in-process computation can be millisecond-scale; COM startup, website fetch, rendering and inference cannot be promised at that scale.

**AI-call frequency/cost.** Target one initial compilation and exception/final assessment calls per task, rather than per primitive; actual count depends on task/uncertainty and must be measured. Program length, retries, token generation and sandbox startup add cost. “Zero additional model call” means known deterministic work only, not zero verifier cost.

**Accuracy/reliability.** Typed contracts, deterministic calculations and native readback can make structured work easier to verify. A bad program can execute many wrong steps quickly; require bounded IR/API surface, dataflow validation, per-effect grants, resource locks and preconditions. Do not give generated Python an unrestricted host shell/COM object.

**Security/recovery.** Compile only within user-issued capabilities. Broker rechecks account/device/task/operation/epoch/deadline/scope before each effect. Journal planned→started→effect committed/unknown→verified; recover by inspecting receipts/output identity, not replaying the whole program. Exactly-once external application mutations cannot be guaranteed merely by a queue.

**Cross-platform.** Windows: discovered registered automation/UIA/files. macOS: declared scriptability/App Intents/AX where granted. Android/iOS: only legitimately exposed intents/documents/actions/integrations; missing broad control is a typed unsupported result. No Windows COM emulation claim.

**Minimal future prototype / paths / complexity.** Scope L (compiler, trusted broker, security), low incremental execution cost for supported APIs; adapter coverage/maintenance is the largest dependency. Reuse src/jarvis/protocol.ts, src/jarvis/task-authority.server.ts, src/jarvis/device.server.ts, jarvis-runtime/ocade_device.py and document helpers. Add an isolated, bounded IR interpreter behind the existing authority, not an arbitrary eval endpoint or parallel planner. Prototype a fresh document, a research→sheet graph and safe file mutation with independent proofs; then unfamiliar-app capability negotiation. Do not implement now.

**Where it fails.** Unknown apps without useful APIs, complex visual canvas workflows, evolving APIs, unsupported permissions, ambiguous goals. Fall back explicitly or block; do not bury dozens of GUI clicks inside a misleading “one action.”

#### Alternative B — reactive semantic controller with event-driven goals

**Mechanism.** The planner selects bounded semantic goals/strategies; a deterministic local behavior tree/state machine maintains predicates over DOM/UIA/AX/app state. Event subscriptions and bounded reads trigger transitions. It selects fresh semantic elements/control patterns and awaits concrete postconditions; it does not ask a remote model to reinterpret every stable screen. Novel semantic ambiguity can request a model mapping; that mapping has a resource/version lifetime. R16/R17/R19 inform the design.

**Distinct from A.** The runtime executes a closed set of audited reactive controllers, not a newly generated arbitrary program. Control is continuously state/goal driven; after a user edit or app event it reevaluates predicates, rather than resuming a stale precompiled instruction pointer.

**Speed/calls/cost.** Many known UI transitions may require no additional inference. Event notifications can reduce polling and needless screenshots. IPC/control-provider delays, app UI threads and tree traversal still matter; UIA events can be missing/coalesced and need timeout/readback fallback. Model calls scale with novel states/ambiguities, not automatically one per task. Maintenance is semantic-controller coverage, not GPU provisioning.

**Accuracy/security/recovery.** Strong target identity + expected control role/state, exact window/document ownership, event receiving/visibility checks and before-effect epoch validation. Independent goal verifier detects success; interrupted actions return RUNNING/UNKNOWN/FAILED rather than model prose. STOP interrupts controllers immediately; Resume rebuilds current state and rechecks goal instead of repeating the last input.

**Cross-platform.** Windows UIA and macOS AX adapters are separate providers with different patterns/permissions. Browser DOM is another provider. Android only policy-compliant action surfaces; iOS participating-app intents, not a fictional AXUIElement cross-app driver. Pixel-only canvas targets require a distinct grounded fallback and may remain unsupported.

**Prototype / paths / complexity.** Scope L (state/event/identity consistency), moderate adapter upkeep. Extend jarvis-runtime/ocade_accessibility.py and jarvis-runtime/actions/browser_control.py through a shared typed observation model, replace unconditional UI sleeps only after predicate-based proof, reuse task authority. Isolated prototype: multi-tab form, unfamiliar native control, focus contention, asynchronously appearing dialog. Must demonstrate both safe refusal and progress with unrelated page animation.

**Where it fails.** Incomplete/inaccurate accessibility trees, custom renderers, missing events, semantic drift, unavailable iOS/Android surfaces. It cannot synthesize a new document/spreadsheet feature merely from knowing a button's role.

#### Alternative C — versioned deterministic skills/RPA with guarded replay

**Mechanism.** Approved task procedures are authored or learned once, validated independently, parameterized, then stored as versioned skills. A skill specifies capability/schema/version prerequisites, local resource bindings, semantic selectors, expected values, effect and recovery graph. Subsequent matches execute deterministically with native/API/DOM operations; the model fills intent parameters or chooses among qualified skills, and may assist repair in a separate evaluation track. R02/R13/R19 are precedents.

**Distinct from A/B.** The hot path selects an already qualified procedure; it neither compiles a fresh general program nor solves a novel goal through a reactive controller. All control logic and allowable variations are versioned before replay. Capability matching must not smuggle a test's exact expected output into a recipe.

**Speed/calls/cost.** A repeat skill can have zero action-planning inference after selection; authoring/qualification/maintenance costs must be included. Cold unseen workflows may be slower than A/B and need explicit escalation. Avoid quoting RPA vendor precision as measured success. Cache hits must validate app/file/schema/user context; an unsafe cached target is not an optimization.

**Accuracy/security/recovery.** Validate parameters/types, output manifests and fresh selectors; lock each shared resource. Persist checkpoints and stable operation IDs; rerun safe reads freely, reconcile ambiguous writes before retry. A failed skill stops; automatic “healing” cannot silently change scope, alter verification, overwrite output or widen credentials.

**Cross-platform.** Portable skill semantics with platform-specific implementations negotiated by capability IDs; use public intents/Shortcuts or human-defined automation where appropriate, respecting Android policy. No assumption that a Windows-recorded macro can run on Mac/iPhone. Unsupported platform implementations are explicit gaps.

**Prototype / paths / complexity.** Scope M for a narrow repeat workflow, L for a general library/qualification lifecycle. Reuse jarvis-runtime/ocade_discovery.py recipes and existing typed document/browser tools; evolve recipe_save into validated versioned artifacts only in future implementation. Benchmark cold authoring and warm replay separately. Keep resource ownership/permission/settlement in current authority.

**Where it fails.** Novel workflows/apps, changed app versions/layout, insufficient examples and overfitting. A fast memorized demo is not general-purpose intelligence. Skill hit/miss/repair rates on unseen tasks are mandatory metrics.

#### Alternative D — hierarchical device actors with local action policies

**Mechanism.** A global planner decomposes work into bounded device/resource goals, while isolated device actors execute locally with semantic grounding and a small/local multimodal action policy for states that need perception. Each actor emits short guarded action chunks, observes locally, and escalates only at ambiguity/risk/goal boundaries. Parallelism exists across genuinely disjoint resources/devices; shared desktop input has one owner. R01 and R20 inspire hierarchy/local inference; this candidate is not a claim UFO or UI-TARS alone supplies the entire design.

**Distinct from A/B/C.** Learned local perception/action policy is the hot control loop, with hierarchical coordination across actors. It can tackle unknown visual interfaces without a pre-existing deterministic skill or a complete API/controller model. Local AI still counts as AI; moving it off the network does not make computation free or deterministic.

**Speed/calls/cost.** Fewer remote reasoning round trips are plausible; per-frame local inference, preprocessing, model load, GPU memory, power/thermal and action chunk errors can outweigh network savings. Count remote planner calls AND every local inference. Commodity CPU/iOS memory limits may make it slower or infeasible. No claim of millisecond VLA inference/whole-task completion.

**Accuracy/security/recovery.** Local grounding must bind frame→target→effect and refuse stale/occluded/protected content. Device actors have restricted capabilities, deadlines and one control epoch, not autonomous rights. Journal each effect/chunk with intermediate verification, risk-adaptive chunk size, local STOP and isolated worker termination. Global DAG correctness does not guarantee Office/chart/content correctness.

**Cross-platform.** Each actor advertises only legitimate native/browser/intent capabilities. Lab Android emulation/iOS XCTest remain lab-only. A local model does not bypass entitlements, accessibility policy or background execution restrictions. Production Standard/High/Offline model policy remains fixed unless the owner explicitly approves additional controller models; experimental local-policy models in isolated prototypes must be declared separately.

**Prototype / paths / complexity.** Scope XL (model serving/grounding/device coordination/security/platform evaluation), higher hardware/operations cost. Reuse Agent/device capability/receipt protocol and current broker; isolate policy worker, avoid a second identity/cancel/settlement authority. Prototype one bounded visual editor goal and one two-device disjoint workflow; compare against semantic-only A/B before adding fleet complexity. Pin and license-check model artifacts.

**Where it fails.** Visual ambiguity, screenshots with hidden data/prompt injection, hallucinated geometry, insufficient hardware, model action errors and cumulative drift. It can reproduce the very slow click loop under a new name if action chunks remain tiny or local inference is slow.
