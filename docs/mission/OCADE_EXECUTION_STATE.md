### Continuation Block 7 — signed, device-bound offline usage

Offline work now draws capacity from the same server-authored commercial
windows before a device disconnects. Free receives independent seven-use
blocks; Pro and Max receive 35- and 70-equivalent blocks. Each block is bound
to one account, active device, browser installation, account window and
monotonic sequence range, signed with an explicitly configured Ed25519 server
authority, and verified in the browser before it enters the local counter.

Refills are independent signed blocks rather than mutations of a usable lease.
This matters under a signing outage: a failed refill can be returned without
invalidating or releasing capacity the device already owns. The server reserves
session and weekly capacity atomically before signing, supports one deduplicated
next-window block per device, and promotes that block at its signed start. Key
rotation retains earlier public verification keys until their leases expire;
the configured private/public pair is self-tested before issuance.

The device counter uses a non-exportable WebCrypto key, Web Locks and an
IndexedDB transaction around a signed append-only hash chain. Free reserves
exactly one use. Paid work reserves the remaining selected block before it
runs, then settles measured work and returns the local remainder, so an output
can never cost more than was held before execution. Replayed logical requests,
forked sequences, forged signatures, wrong identities, future/expired leases
and material clock rollback fail closed.

The signed-in root mounts one non-blocking synchronization bridge. It
registers the canonical device, reconciles event chains before requesting new
capacity, refills at 25 percent remaining, persists one future block, and
publishes usage changes to Settings. The usage UI separates online in-flight
reservations from offline device allocation and never exposes paid raw
capacity. Missing signing configuration is a truthful unavailable state.

### Continuation Block 8 — one commercial permit before every intelligence path

logical request before any query classification, engine initialization,
provider routing or computer-observation model transport. Connected work uses

cryptographically verified device allocation. A transient online transport
failure may reuse the same generation and idempotency identities with an

The shared Chat/Cowork runtime requires the permit in its public TypeScript
contract and validates it again at runtime before even the conversational
short-circuit. Chat's main sends, side questions and reruns, Cowork missions,
and the Copilot screen-observation surface all name their commercial surface
explicitly. Tool loops, retries and fallback retain that permit rather than
acquiring another one. Meaningful output finalizes once; cancellation or total
failure before output releases once.

Authenticated server agent transports no longer trust a browser-held object.
They require the complete permit identity and atomically claim its durable row
for the authenticated account, exact generation, idempotency key and surface.
The claim succeeds only once while the row remains reserved and unexpired,
closing the concurrent-replay gap that a read-only validation would leave
before importing the model or native adapter. Released or expired permits may
be reserved again safely because the new reservation clears the old transport
claim. A signed offline permit is explicitly unable to authorize a server-side
intelligence transport.

### Continuation Block 9 — one normalized intelligence authority

`OcadeIntelligence` is now the single browser-safe backend contract. It
validates the commercial permit before any probe or initialization, normalizes
status, tokens, tool calls, tool results, usage, refusals and final responses,
and owns Automatic, Online and Local-only selection. Automatic fallback is
allowed only after a retryable online failure that produced no meaningful
output and reuses the same permit. Online never falls back silently. Local-only
never probes or fetches the online transport. Cancellation propagates through
the router to the active transport.

The existing local Brain remains the model authority; it is adapted rather
than duplicated. The shared query runtime, every internal tool-loop turn,
Cowork's mission brain and session-memory extraction now cross the same router
with the originating permit. The latter remains an explicit background
continuation, so it neither creates a second commercial run nor takes over the
visible engine state. A whole-tree negative gate rejects a future direct model
call from these authorities.

The secure online boundary is a portable Web-standard handler exposed by one
Supabase Edge Function. It validates method, content type, origin, request size,
JWT, checked-in provider model, consent and the durable permit claim before
provider I/O. It streams normalized SSE, handles CRLF and fragmented event
boundaries, retries only bounded pre-output transient failures, aborts provider
work when the browser cancels, and logs neither content nor credentials. The
browser transport is disabled unless explicitly configured and sends only the
session token and public Supabase key; provider and service credentials remain
server-side.

The production journey found and fixed one real fail-closed UX regression:
when no permit could be issued, Chat initially left the attempted message only
in the composer. It now records the attempted turn with an explicit non-answer
while still performing no inference and charging nothing.

### §8 a conversation that leaves nothing behind, and memory you can carry

Two of §8's list. `incognito` appeared nowhere in Chat — only in the
browser-control policy, which is a different thing — and the memory panel had
review, edit, pause, reset and deletion but neither of the two that let
somebody carry what OCADE knows about them or check it.

Both are the kind of privacy requirement whose PARTIAL version is the dangerous
one, so both were built at the choke point rather than the call site.

INCOGNITO. `persistChatMessage` refuses before it chooses a destination, so all
seven call sites in the chat screen are covered by one rule — a guarantee
spread across seven `if`s holds until somebody adds an eighth. The conversation
itself is never created: `createConversationLocally` writes a record and queues
it for the server, and a conversation row is a record of the conversation
having happened. Memory is excluded in BOTH directions, not written and not
read, because excluding only the write is the weaker half: somebody who goes
incognito is saying "do not connect this to me", and a reply shaped by what
OCADE remembers about them connects it.

Three gestures had to be refused rather than quietly half-done. Branching
copies the earlier messages into a NEW conversation, which is the one gesture
that would turn "nothing is saved" into a saved transcript. Deleting would
write a tombstone — a durable row saying the conversation was deleted. Export
would create the durable copy the mode promised not to. Each says so.

Two bugs the mode created and which are fixed: a list refresh would have made
an open incognito conversation VANISH mid-sentence (it is in no list the
refresh reads), and the message-load effect would have wiped its transcript by
asking storage for messages that are only in React state.

The banner states the limits as well as the promises, and the one that matters
is that an online request still reaches the provider that answers it. A person
who believes "incognito" means the request never leaves the machine may type
something they would not have.

MEMORY IMPORT AND EXPORT. All or nothing on import: a file with one malformed
row is refused entirely, because a partial import leaves somebody with a memory
set that is neither what they had nor what they were restoring. Every imported
row is marked `imported` whatever the file claimed — the source field answers
"where did OCADE get this idea about me". The `enabled` flag is not exported,
so opening a file cannot turn memory on somewhere it was deliberately turned
off.

**The export read the screen, not the store.** First version serialised the
`rows` state — and this panel deliberately shows no rows while memory is
PAUSED, so the file would have been empty and would have said "Exported 0
memories": a confident, false answer to the one question the export exists for.
It reads the authority now, and the portability controls sit OUTSIDE the
enabled guard, because the person most likely to ask what OCADE knows about
them is the one who has just turned it off.

**An accessibility defect I introduced and the gate caught.** The import input
was `sr-only` inside its label: a keyboard stop with nothing to see. The repo's
own pattern is `peer sr-only` with the ring on the label — and the input has to
be a SIBLING, because Tailwind's `peer-*` compiles to a sibling combinator, so
the nested version would have satisfied the gate while showing no ring at all.

Browser-proven: an incognito message writes zero new IndexedDB keys and appears
in no local storage, the banner states its limits, the conversation is gone
after a reload, memory exports to a named file, an import is read back and
shown, and a file OCADE does not understand is refused without touching what
was already there.

### §8 side conversations, delete-all, and four controls that did nothing

SIDE CONVERSATIONS. `src/lib/chat/side-conversations.ts` is the whole authority:
a short thread hanging off ONE message, stored in the same `chats` data class
under a `side:` key prefix, rendered UNDER its anchor through `MessageList`'s
`renderFooter` slot rather than as a message.

It is NOT a branch, and §8 lists them separately because they solve opposite
problems. A branch says "take this conversation elsewhere from here" and
produces a SECOND conversation carrying a copy of everything before the fork. A
side conversation says "hold on, one question" and produces nothing in the
sidebar: it belongs to the message it hangs off, travels with it, and is deleted
with it.

The key prefix matters more than it looks. A side record carries
`conversation_id`, and `loadChatMessages` filters on exactly that — so without a
key the transcript loader can EXCLUDE, every side question and its answer would
appear inline in the transcript and be sent to the engine as part of it, which
is precisely what somebody asking a side question asked not to happen. The
exclusion was fault-injected: removing it turns a one-message transcript into
three.

The engine is sent the ANCHOR and the SIDE THREAD, never the conversation.
`sideConversationPrompt` is pure and takes no transcript, so there is no
parameter one could arrive through. The reason is not only cost: sending the
whole conversation would make a two-word clarification consume the same
commercial allowance as a full turn, and answers to "what does this word mean"
would drift back toward whatever the conversation was about. It goes through
`beginBilledRequest` before `reason()` like any other generation — a surface
that skipped the permit would be a way to spend an allowance nobody counted.
Incognito is INHERITED from the conversation rather than decided again.

DELETE-ALL. Message bodies are removed outright; conversation records are
TOMBSTONED. The asymmetry is deliberate: a tombstone for a message body would be
a record containing the text it claims to have deleted, and removing a
conversation record outright would let another device re-synchronise the
conversation straight back. `deleteAllVaultMessages` makes one pass over the data
class rather than one per conversation — the operation that clears everything is
the one most likely to be run on a large history. The server function accepts NO
id list: a request that could name what to clear could name somebody else's.

**Four controls in the transcript did nothing when pressed.** One `actions`
object is drawn for every message, so "Branch from here", "Save this answer",
"Ask about this" and "Regenerate answer" rendered on USER turns as well as
answers. Every handler checked the role and returned without acting — so the
controls were visible, focusable, keyboard-reachable, and inert. The role check
now decides the RENDER as well: a control that cannot act is not offered.
Regenerate and re-run additionally need `isLatest`, which only the transcript
knows, so `MessageList` passes it. The handlers keep their guards as defence
against a caller passing the wrong thing.

**A dead component was hiding a vacuous assertion.** `MessageRow` and its three
helpers — 180 lines in the chat route — were referenced by nothing; the
transcript has rendered `MessageBubble` for a long time. `chat-phase5-source`
asserted `title="Save to Artifacts and Activity"`, a string that existed ONLY in
that dead component, so the gate was passing against source nobody could reach
and would have gone on passing with the real save button deleted. Removing the
dead code exposed it; the assertion now checks the live control where it is
rendered and the handler where it is wired.

**The fixture reported every delete as removing nothing.** `stub-supabase`
answered a `count: "exact"` delete with an `x-removed` header, which supabase-js
knows nothing about — it reads `content-range`. `deleteAllConversations` returns
that count to the screen, so somebody who had just cleared four hundred
conversations would have been told none were deleted. Fixed in the fixture.

Browser-proven, in the §8 journey: the seeded conversation opens with two
messages, the side-question control appears on the ANSWER and not on the prompt,
the panel opens under its anchor and says the question stays out of the
conversation, focus moves into it, asking leaves the transcript at exactly two
messages with the question nowhere in it, and OCADE says why it could not answer
in a sandbox with no engine. Delete-all is inert until the phrase is typed, says
what it spares, leaves no message body in browser storage — and OPFS still holds
`ocade-models` afterwards, so Offline Intelligence survived, which is the
promise the dialog makes.

### §8 sharing a conversation, which is the one §8 capability with a stranger in it

The last item on §8's conversation list. Everything about it is shaped by the
fact that it hands a person's own words to somebody with no account.

A SNAPSHOT, NOT A WINDOW. `ocade_conversation_shares` stores the transcript as
it was WHEN IT WAS SHARED. A live view would keep publishing whatever was said
next — somebody shares an exchange, carries on privately in the same thread, and
every later message is on the public link without a further decision. That is
not a subtle failure mode; it is the obvious one, and it is why a share costs a
`jsonb` column. Fault-injected: turning the reader into a live view puts a
message added afterwards on the link.

NO ATTACHMENTS. The snapshot carries role, text, time and an attachment COUNT.
"Share this conversation" is not consent to publish the documents read during it,
and a file name alone can disclose more than the conversation does — the schema
test shares a conversation whose attachment is named `severance-agreement.pdf`
and asserts the name is nowhere in the snapshot.

ONLY A SYNCHRONISED CONVERSATION CAN BE SHARED. A Browser-Only or PC Vault
conversation's messages are on the person's own machine and deliberately not on
the server, so a share built from `ocade_messages` would be an EMPTY transcript
published under a real title — a silent wrong answer. `PT409` with
`conversation_not_synchronised`, and the interface names the remedy. An
incognito conversation has no row and is refused in the dialog without a request.

THE TABLE IS NOT PUBLICLY READABLE. Public access is one SECURITY DEFINER
reader taking the token and returning four fields. `owner_id` — a real account
identifier — never leaves the database, and the link cannot be used to enumerate
shares. A revoked, expired and never-issued token are answered identically: a
distinguishable "this was revoked" would confirm a guessed token had once been
real.

REVOCATION IS REAL AND IS NOT THE ONLY ONE. `revoked_at` stops the reader, an
optional `expires_at` stops it by itself, and the foreign key means deleting the
conversation — including through §8's delete-all — takes the share with it. A
partial unique index allows one live link per conversation, so "stop sharing
this" is a complete sentence rather than one of two links.

**THE SECURITY GATE SAID NO, AND IT WAS RIGHT TO.** `security-definer.test.ts`
and `db-twin.test.ts` both refuse a `SECURITY DEFINER` function that is
anon-callable or ignores `auth.uid()`, and the reader is deliberately both. The
fix was NOT an exemption. `TOKEN_AUTHORIZED_FUNCTIONS` is a named class with a
HARDER test attached: a function in it must take a token parameter, must filter
on it, must return no account identifier, and must answer nothing for a token
nobody issued — four assertions the blanket rule never made. A function that
cannot pass them fails whether or not it is named there, and a name for a
function that no longer exists fails too.

**THE TWIN COULD NOT SEE THE FIELD THE PRODUCT BRANCHES ON.** `db-twin.mts`
returned a refusal's message string and nothing else, so a test could not tell
`not_found_or_forbidden` from `conversation_not_synchronised` — a distinction
these functions deliberately hide from callers and deliberately keep for tests —
and would have had to match on prose. It now also returns `errorCode` and
`errorDetail`, the SQLSTATE and `DETAIL` that PostgREST turns into an HTTP status
and `error.details`. `error` is unchanged, so every existing assertion still
reads what it read.

**THE FIXTURE REPORTED EVERY DELETE AS REMOVING NOTHING** — see the §8 entry
above; the same `content-range` fix.

NOT INDEXED, TWO WAYS. A share link is unlisted and that IS its security, so
indexing would turn "anyone with the link" into "anyone who searches". The page
carries `noindex, nofollow, noarchive, nosnippet` and `robots.txt` disallows
`/share` — a well-behaved crawler reads the file before fetching the page it
would need to fetch to see the tag. `ssr: false`, so the transcript is never in
the HTML of a response where a proxy, a log or a cache could hold it.

Browser-proven, with two browser contexts: opening the Share dialog publishes
nothing and says the copy is frozen BEFORE anything is created; creating a link
yields a 48-hex-character token; a fresh signed-out context reads the
conversation with no account and is not asked for one; the page carries
`noindex` and `robots.txt` disallows the route; no account identifier appears on
it; and after "Stop sharing" the same URL serves nothing and does not admit the
link was ever real. The DATABASE half of the authorization is proven separately
under `SET ROLE anon` against real PostgreSQL, because the fixture answers an
unauthenticated request as the seeded account and a claim made against it would
be a claim about the fixture.

### §L help publishing, and a bundle regression the gate caught twice

SUPPORT-001 carried the same incorrect blocker STATUS-001 did — "Supabase work

THE SOURCE CATALOGUE STAYS AND STAYS THE FALLBACK. The twenty-one answers are

The reader seam: `searchArticles`, `faqViewMatching`, `findArticleIn`,

### §K incidents: a gap that was recorded as blocked and was not

STATUS-001 — incident creation, timestamped history, maintenance scheduling and

`ocade_status_incidents` and `ocade_status_incident_updates`, with:

- APPEND-ONLY HISTORY. There is no update or delete path to the updates table

- RECENT STRONG AUTHENTICATION, from the §B authority. Publishing is a public
  statement in OCADE's name.

announced, over — because a reader and a machine both need to tell next

outage does not end because somebody expected it to.

### §21/§G what a workspace allows its members to use

`PLAN.md` §21 asks for "capability policy" and "connector tool permissions";

Two vocabularies already existed and neither was a policy.
`capabilities/registry.ts` answers whether a capability works on THIS DEVICE;
`agent/domains.ts` groups the tools the router loads. The policy is expressed
in exactly those, so withholding "Computer control" withholds the thing a
person sees named that, and withholding an area removes a coherent set rather
than a list of individual tool names that would go stale the day one is added.
`conversation` is deliberately not withholdable: it is the one area that
touches no machine, and a workspace that withheld it would leave its members
with a product that cannot answer them.

STORED AS WHAT IS TAKEN AWAY, never as what is allowed. A row listing
everything permitted would have to be rewritten every time OCADE grows a
capability, and the day somebody forgot, an existing workspace would silently
lose a feature it had never decided anything about.

THE STRICTEST ORGANIZATION WINS, because somebody can belong to several and the
capability badge and the agent loop have no "acting as" selector to consult.
Belonging to a second workspace is not a way to opt out of the first one's
rules.

replaces a withheld capability's status with UNAVAILABLE and NAMES the

anyway; and the two server functions that run the loop read the ceiling from
the database as the caller rather than accepting one the browser sent. Both
loop points were fault-injected.

### §G/§B a workspace could be deleted by whoever found the laptop open

`PLAN.md` §G asks for "recent reauthentication and AAL2" on the admin surface,
and §B names ownership and organization deletion as high-risk explicitly.
OCADE already had the rule and already enforced it — `assurance.ts` is pure and
exhaustively tested, and `requireAssurance(HIGH_RISK)` sits on every server
function that deletes an account, revokes sessions or changes a second factor.

The organization mutations are not server functions. They are RPCs the browser
calls DIRECTLY through PostgREST, so the middleware never ran in front of them.
An authorized owner's open tab, ten seconds, and the workspace was gone.

The rule now runs where the grant is. `ocade_require_recent_strong_auth` is
called inside `ocade_delete_organization`,
`ocade_transfer_organization_ownership`, `ocade_set_organization_member_role`
and `ocade_remove_organization_member`, and it reproduces `assurance.ts` rather
than reinterpreting it: AAL2 for enrolled accounts, recency for everybody, an
unknown proof time treated as not recent, a proof dated in the future rejected.
The ten-minute window is one number — a test asserts the SQL interval equals
`RECENT_PROOF_MS`. `ocade_set_organization_member_state` is deliberately NOT
guarded: deactivation is the cautious, reversible action an administrator
reaches for when they are unsure, and the one thing somebody locked out of
their authenticator still needs to do quickly.

Refusals come back as PostgREST `PT403` with a stable token in DETAIL, so the
screen offers the right door. `ConfirmIdentity` shows a link to the challenge
for `factor_required` and a password field for `reauthentication_required`, and
answering it RETRIES the refused action — being made to retype an
organization's name after a security prompt is how people learn to keep
sessions permanently unlocked.

Two more defects came out of the same trace.

`SignInMethodsPanel` skipped its password check whenever the session was
`aal2`. That is precisely the case `assurance.ts` documents as the reason
recency exists, so a passer-by could move the address a password reset is sent
to — which is the same as taking the account. It now asks the one rule.

The danger zone cleared the typed confirmation on EVERY outcome, including a
refusal somebody is meant to answer and continue from. It clears on success
only.

The password proof itself was written out twice and had already diverged; it is
now `proveIdentityWithPassword` in `src/lib/security/reauthentication.ts`, used

**A gate that a comment could satisfy.** `account-safety.test.ts` asserted that

### §L help-article locales: the mechanism, and the honest answer for the rest

Every article declared `locale: "en"` — which is not a tag `SUPPORTED_LOCALES`
recognises, so every comparison against a reader's locale was against a value
that does not exist. That is now a real tag, and articles can carry a
translation per locale.

the original — and SAYS which it gave you. A German reader gets the English

fabricating the evidence the requirement asks for.

same one. SUPPORT-002 is EXTERNALLY-BLOCKED on human translators, with the
repository-controlled part complete and the interface verified truthful.

### §O ownership safety, which the organization model made both applicable and urgent

DATA-002 was recorded NOT-APPLICABLE because OCADE had no ownership model.
Building one made it applicable — and made it urgent in two directions at once,
neither visible until somebody actually deleted an account that had a team:

- `ocade_organization_members.user_id` is `ON DELETE CASCADE`, so deleting the
  identity removes the membership with no OCADE code involved anywhere. Every
  last-owner check lived in a function, and this path called none of them. An
  organization could be left with nobody who can administer it, by the one route
  that never touched the protections.
- `ocade_organizations.created_by` was `NOT NULL ... ON DELETE RESTRICT`, written
  to make the database refuse the unsafe order. It refuses at
  `auth.admin.deleteUser`, which the deletion path runs LAST — after the profile,
  devices, conversations and tickets are already destroyed. The person would be
  told "Account records were removed but sign-in deletion failed" and left with a
  gutted account they could still sign into. Provenance is not authority.

Both fixed in `20260904140000_organization_ownership_before_account_deletion.sql`:
`created_by` is nullable with `ON DELETE SET NULL`, and the invariant moved into
a BEFORE DELETE trigger on the membership table, which is the only place that
runs on a path nobody wrote. The trigger allows the cascade from an organization
being deleted (the parent row is already gone by then) and refuses the one that
is a last owner walking away.

`ocade_organizations_blocking_deletion` answers the question the deletion path
asks BEFORE it destroys anything, and the Delete-account screen asks the same
question before the button — naming the organizations, separating the ones that
can be handed over from the ones the person is alone in, and linking to where
that is done. Fault-injected: disabling the trigger lets the last owner's account
be deleted, and the suite catches it.

### §F organizations, and four privilege defects the schema gate found

`/organization` was the one canonical route in §4's table that nothing served,
tracked as ORG-001. It is now `supabase/migrations/20260904120000_ocade_organizations_and_membership.sql`
(organizations, membership, invitations, groups, an audit trail, and fourteen
guarded mutations), `src/lib/organizations/*`, `/organization` and `/invite`.

WHY IT IS NOT BUILT ON `tenants`. `tenants` and `tenant_members` already exist
in this schema and were the obvious shortcut. They are FICIA's company-entity
model — registration number, tax ids, fiscal year, and roles owner, manager,
employee, accountant, auditor, consultant, advisor. That vocabulary describes a
BUSINESS. OCADE's question is who may act inside a workspace, which has three
answers. Building on them would have made one product's roles mean something
else in another.

FOUR DEFECTS, EACH FOUND BY RUNNING SOMETHING RATHER THAN READING IT:

1. **A privilege escalation.** `ocade_org_can_administer` was
   `SELECT role IN ('owner','admin')`, and for a non-member `role` is NULL — so
   it returned NULL, and every guard written `IF NOT can_administer(...) THEN
   RAISE` never took its branch, because `NOT NULL` is NULL. An account owning a
   DIFFERENT organization removed a member from this one and got `1` back. The
   behavioural suite caught it on its first run. Fixed with `COALESCE` and a new
   `ocade_org_is_owner`, and pinned by a suite that asks every mutation the same
   question: an outsider must be REFUSED, out loud.
2. **`anon` could execute three SECURITY DEFINER helpers**, because PostgreSQL
   grants EXECUTE to PUBLIC by default and the migration only granted to
   `authenticated`. Caught by the existing db-twin gate.
3. **Supabase's default privileges were invisible to the twin.** A real project
   carries `ALTER DEFAULT PRIVILEGES ... GRANT ALL ON TABLES`, so every new table
   is born with INSERT/UPDATE/DELETE granted DIRECTLY to `authenticated`, and
   `REVOKE ... FROM PUBLIC` does not remove a direct grant. The twin had none, so
   it proved "authenticated cannot write these tables" while production had handed
   it every write on all six. The twin now reproduces the real project's default
   ACLs (taken from `pg_default_acl`, postgres's entry, which excludes `anon`).
4. **Two older migrations had the same hole**, exposed the moment the twin
   became truthful: `legal_consent_receipts` granted UPDATE and DELETE to
   `authenticated` despite being documented append-only, and the billing/support
   ledger granted every write on payment events and invoices. Row-level security
   refused all of it throughout — no table with RLS off has write grants — so
   nothing was exploitable; the privilege layer is now closed too, in the
   migrations themselves and in `20260904130000_revoke_default_privilege_writes.sql`
   for the already-applied database.

The db-twin's "definer function binds its caller" gate was also strengthened
rather than exempted: it read each function's own text for `auth.uid()`, which
would have forced fourteen exemptions reading "a stranger may reach these rows".
It now computes caller-scoping as a fixpoint through called functions, so a
shared authorization helper is recognised and a genuinely unbound function is
still caught (fault-injected to confirm).

Applied to the live project and verified: all six organization tables and the
audit writer are read-only to `authenticated`, consent receipts are
select+insert only, payment evidence is select only.
