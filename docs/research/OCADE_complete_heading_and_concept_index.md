## Part C — Additional headings and concepts gathered after the source text

**Distinct from the source:** the following are requirements, refinements and historical lessons established in our subsequent conversation/research; they should not be misrepresented as literal headings from the uploaded TXT.

### Product and user experience

1. **Zero-effort customer workflow** — The customer supplies the outcome once; the product handles routing, execution, recovery and delivery within authorised boundaries.
2. **Centered minimal prompt** — Start on a clean screen without a prominent dashboard, orb or complicated tool interface.
3. **Collapsed task input on Send** — Turn the prompt into a compact running experience immediately after submission.
4. **One subtle ambient status line** — Show one truthful, changing plain-language action beneath the prompt, not a large progress box.
5. **No script filenames in customer UI** — Keep source paths and subprocess names within optional diagnostics, not the ambient status.
6. **Small expandable activity link** — Reveal meaningful execution receipts and blockers only when the customer chooses to inspect them.
7. **Small collapsible history sidebar** — Provide old tasks and conversations without occupying the main workspace.
8. **Final answer and file links** — Keep completion clean, with actual verified deliverables and correct download paths.
9. **Minimal monochrome styling** — Use restrained visual hierarchy and accessibility rather than attention-grabbing ornaments.
10. **Non-prominent STOP access** — Provide genuine cancellation via small site control and device tray, not an oversized UI component.
11. **Task-adaptive deliverables** — Provide final files and optional editable originals when the task calls for them; avoid unnecessary result clutter.
12. **Autonomous reversible defaults** — Resolve minor ambiguity with safe reversible choices rather than repeated confirmation dialogs.

### Device, permissions and login

13. **One installer, automatic trusted pairing** — Install a signed companion once, then auto-discover devices on the same account after appropriate mutual device trust.
14. **Signed Device Agent** — Runs task actions on the customer-owned computer using scoped authority instead of a hidden cloud desktop.
15. **Same-account device discovery** — Discover likely eligible devices without assuming common login grants unrestricted device control.
16. **Persistent authorised capability scopes** — Remember legitimate permissions and avoid asking again on every routine action.
17. **Official Windows elevation** — Use genuine UAC for protected operations; never emulate credentials or bypass administrator protections.
18. **Protected payment/secret boundary** — Pause at payment authorization, passwords, MFA/passkeys or sensitive scope changes while continuing independent work.
19. **Google-first product sign-in** — Offer the preferred simple sign-in surface without conflating product authentication with external website access.
20. **Existing authorised browser session** — Prefer browser integrations that respect the actual session/profile and do not copy, read or extract stored secrets.
21. **Session expiry and reauthentication** — Refresh credentials only through supported flows; otherwise request an official login step.
22. **MFA/CAPTCHA handling** — Let customers complete external security challenges without bypassing them.
23. **Explicit-recipient outbound actions** — Perform authorised sends to recipients named in the task; handle untrusted recipients and risky actions cautiously.
24. **Safe deletion to Recycle Bin** — Prefer recoverable deletion and preserve originals where appropriate; irreversible actions need stronger authorization.
25. **Secrets vault and token isolation** — Keep credentials out of prompts, logs and generic MCP process environments unless their scope requires them.

### Real computer control and execution

26. **Dynamic Windows application catalog** — Inventory Win32, UWP/MSIX/Store, Start Menu aliases, associations, running processes and capabilities.
27. **No hardcoded application journeys** — Choose tools by capabilities and current installation evidence, not app-specific demo macros.
28. **Exact PID/HWND/document binding** — Target the correct account, process, window, tab and file; fail closed on ambiguity.
29. **Window resize, DPI and multi-monitor resilience** — Requery controls and scale coordinates only when needed; test changed layouts and virtualized controls.
30. **Minimized/hidden-window truthfulness** — Use native APIs for background work; restore when needed, because UIA and synthetic input cannot universally operate hidden windows.
31. **User take-over and conflict handling** — Pause affected UI actions when the user edits or changes focus while independent background operations continue.
32. **Native-first execution order** — Prefer supported APIs/object models, scoped commands and file/project formats before DOM/UIA and visual coordinates.
33. **Browser DOM and authorised network calls** — Use Playwright or documented APIs without treating a website as permanently automatable.
34. **Local bounded filesystem workspace** — Keep task inputs, intermediates and outputs isolated with provenance, rollback and ownership.
35. **Resource-aware scheduler** — Run independent work in parallel but serialize conflicting document, tab, application or file mutations.
36. **Transactional task/side-effect journal** — Record intended and observed changes, acknowledgements and idempotency keys before repeating effects.
37. **Durable checkpoints and recovery** — Restart from independently verified state after crash, disconnect or model outage.
38. **Local STOP safety fence** — Prevent new actions after STOP and accurately report any already committed or in-flight effects.
39. **Bounded receding-horizon planner** — Keep large goal milestones while adjusting immediate actions to current observations with explicit retry limits.
40. **Independent professional verifier** — Check spreadsheet values/formulas, document structure, video metadata, CAD geometry and required output quality.
41. **Capability-first tool choice** — Prefer a verified equivalent installed app if the named software is unavailable and the user did not require that exact app.
42. **Untrusted MCP provenance restrictions** — Do not execute unfamiliar registry packages solely because they advertise a matching tool.
43. **MCP self-install under established policy** — Prebundle trusted tools and automatically provision approved, pinned components without customer terminal setup.
44. **No forced local model fallback** — Respect the separate offline Chat capability; desktop execution should not silently switch to an unapproved local planner.

### Lessons from earlier failures and implementation discipline

45. **Pairing and agent-runtime blocker** — Verify the companion is installed, authenticated, paired and reachable before promising any PC action.
46. **Incomplete app discovery** — Account for Windows built-ins and packaged apps; never invent launch commands.
47. **Wrong OS command context** — Bind script generation to the actual Windows shell, environment and permissions.
48. **Wrong-window incident** — Use exact leases and fresh identity checks; opening the wrong window is a critical safety failure.
49. **Blocked vs executed tests** — Historical browser QA showed 20 PASS, 5 FAIL, 8 PARTIAL and 8 BLOCKED, with no completed real PC workflow; blocked dispatch is not proof of tool failure.
50. **Retired previous engine** — The implementation branch retired the old execution engine; the new foundation requires actual coding, not simply configuring an old runner.
51. **No premature PASS claims** — Treat source inspection, mocks, browser tests, real Windows tests and physical hardware validation as distinct evidence.
52. **Cloud-first testing** — Run all permitted cloud and simulated checks before seeking owner permission for local-PC operations.
53. **Representative real-task benchmark** — Measure completion, safety, accuracy, recovery, latency and necessary user interventions on genuine multi-app tasks.
54. **90% acceptance target, 95%+ ambition** — Use independently verified outcomes and avoid claiming a guaranteed universal 98% or 100%.
55. **Zero known critical safety defects** — Do not accept the build with confirmed privilege, wrong-target, destructive-action or data-leak defects.
56. **No fake deliverables** — Do not let the test harness create the files that the product agent was supposed to produce.
57. **Proof-driven debloating** — Delete obsolete code only after tracing callers and establishing functional parity and regression coverage.
58. **Source code versus verified implementation** — A design heading or LOC projection does not prove that a corresponding runtime feature has been implemented.
59. **Owner-controlled GitHub policy** — Use only the implementation branch; never merge main, deploy, spend, enable payments or use the owner’s PC without authorization.
60. **User-facing MCP invisibility** — Keep plugin discovery, setup, tool selection and process management internal so customers see direct task completion.
61. **First vertical-slice milestone** — Prove one end-to-end authorized task through the actual product surface before scaling to arbitrary apps.
62. **Gradual coverage expansion** — Add browser, spreadsheets, media, CAD and complex cross-app work using common infrastructure with real proof.
63. **User effort as a formal metric** — Count required prompts, security approvals, re-logins and manual fixes in task benchmark results.
